- StudioNet confirmed from docs + probe: RPC `https://studio.genlayer.com/api`, chain 61999 (0xf22f), explorer `https://explorer-studio.genlayer.com`. All chain config in env; no hard-coded timing/counts.
- Contract runner pinned to `py-genlayer:1jb45aa8ynh2a9c9xn3b7qqh8sm5q93hwfp7jqmwsfhh8jpz09h6` (same as Roast, known-good on StudioNet).
- Followed Roast patterns to avoid repeat mistakes: header first line with no comment under it; `while` loops only (no for/sorted/lambda); no storage writes inside nondet blocks; `TreeMap` + `@allow_storage` dataclasses; `gl.vm.run_nondet_unsafe` with independent validator re-run; `gl.nondet.web.get` + `gl.nondet.exec_prompt(response_format="json")`; `gl.vm.UserError` with `[EXPECTED]`/`[LLM_ERROR]`; payable via `gl.message.value` + `_Recipient.emit_transfer`.
- Scoring tolerance ±1 per criterion + accessibility match (docs Pattern 2: numeric tolerance for LLM subjectivity). Reasons stored but not compared.
- UNSCORABLE + one resubmission instead of zero (blueprint §5).
- Appeal bond 0.1 GEN; refund-on-change, forfeit otherwise. Documented as demo accounting.
- Frontend: Next.js App Router + `genlayer-js` single wrapper (`src/lib/genlayer.ts`); reads via `readContract`, writes via connected wallet (injected/EIP-6963 provider). MOCK_MODE until contract address set. No wagmi dependency — EIP-6963 discovery covers Rabby/Zerion/MetaMask/Coinbase; WalletConnect project id reserved in env.
- Reviewer-driven storage fix (resubmission): `contests`/`entries` were `TreeMap[u64, …]`; every doc example declares only `str`/`Address` keys, and the acceptance harness rejects integer keys — so the correction is valid. Both maps are now `TreeMap[str, …]` with `str(int(id))` at all 47 lookup sites; public API (integer ids) and views are unchanged, so the frontend needed no changes. Verified: lint clean, 22/22 direct tests pass (full lifecycle through the str-keyed storage path), redeployed fresh.
- SDK deviation (recorded per blueprint §0): docs describe `estimateTransactionFeesForWrite` / `waitForFinalization` / `client.connect()` / `isSuccessful`, but installed `genlayer-js@1.1.8` exposes `writeContract` + `waitForTransactionReceipt({status: ACCEPTED})` + `provider` in `ClientConfig` and no fee-estimate API. Verified live: `simulateWriteContract` exists but swallows revert reasons (generic "execution failed"), so the app relies on client-side pre-validation + contract `[EXPECTED]` messages via the settled receipt. Upgrade to the fee-profile flow when the SDK is bumped.
- Permissions (changed after live testing): `close_entries` and `judge_entry` are organizer-only; `cancel_contest` was already organizer-only. Blueprint §5 had close/judge as anyone-callable, but the owner wants the launching wallet to run the contest. Trade-off: if the organizer disappears mid-contest it stalls (no permissionless fallback) — accepted for now, revisit if needed. `finalize` stays permissionless (deterministic tally, cannot alter the outcome); `submit_entry` open to all; `appeal` creator-or-organizer; `claim_prize` winner-or-organizer.
- No-winner refund (found live-testing): an all-unscorable contest finalizes with winner 0 and previously nobody could ever claim — prize stuck. `claim_prize` now lets only the organizer reclaim in that case (new `refunded` flag in the return).
- Receipt honesty: 1.1.8 `waitForTransactionReceipt(ACCEPTED)` can return before execution settles, and revert reasons don't always surface in the receipt object — the app once showed "done" for a reverted cancel. `submitWrite` now polls `getTransaction` until the execution result is populated and only reports success on a non-failure execution name; unsettled timeouts report "accepted but not settled" with an explorer link, never "done".
- Blueprint deviations: none from contract semantics; appeal window fixed at 3 days (configurable later); `list_contests(status, offset, limit)` instead of cursor for simplicity.
